# 图片摘要与解读的细粒度测评设计

本仓库把“生成”和“测评”拆成独立阶段。每张图片分别生成摘要、解读，两份答案各自评测。待测模型为本地 Qwen3.5-35B-A3B，模型目录由生成脚本预留；本阶段交付代码、提示词、量表及可离线转交的请求文件，不调用明天才提供的评审接口。

评测的关键是先看原图形成独立证据，再核验候选文本。另一台大模型直接写一份答案不能自动成为 ground truth：它也会误读数字、补造菜名或推测过敏原。本设计将模型标注称为“事实参考草稿”，把人工确认后的版本标为 human_verified，并在报告中区分两种状态。

## 1. 数据与运行边界

输入目录为“图片总目录/语种目录/截图或实拍目录/图片文件”。具体下级目录名不作为识别内容的证据；图片本身决定场景。截图与实拍统一生成和评测，保存语种、来源类型、相对路径、图片哈希等元数据以便事后分组分析。菜单与餐厅照片分开报告，餐厅照片在原解读提示词中对应通用模块。

原图扫描与生成只在允许访问数据的机器上执行。仓库只放代码和配置，不放原图、模型权重、生成答案、参考标注、评审请求或评审结果。路径、输出文本和事实表也可能承载内部信息，不能因为不含图片就视为可以外传。华为数据只进不出的要求意味着后续评审应部署在允许的数据边界内：使用获准的内部接口/网关或本地视觉评审模型。GPT 是否可用要以实际接口的数据处理许可为准；当前实现没有发起外部请求。

跨平台通过稳定 image_id、图片 SHA-256、候选文本 SHA-256、规范化参考 JSON SHA-256 关联，而不是依赖另一台机器上的绝对路径。评审回包还必须原样携带请求提供的 judge_prompt_sha256（64位十六进制字符串），以绑定实际评审提示词。实际视觉接口必须加载允许访问的原图像素，仅提供文件路径不能视为已看过原图。模型、依赖和代码提前进入内网；生成运行不应自动联网下载缺失权重。

## 2. 五个阶段与输出职责

具体命令以 README 为准。参考请求保存在 requests/reference.jsonl，评审请求保存在 requests/judge.jsonl；事实表为 references/<图片ID>.json，评审结果为 judgements/<图片ID>/<任务>.json；报告目录包含 reports/aggregate.json、per_sample.csv、review.csv、report.md。以下阶段保持独立，避免将生成结果混入参考标注：

| 阶段 | 输入 | 保存的产物 | 可复核内容 |
| --- | --- | --- | --- |
| 图片索引 | 原图目录 | 图片清单、元数据、哈希 | 扫描数量、语种、截图/实拍、重复图片 |
| 两任务生成 | 原图、固定 v04 提示词、本地模型 | 每张图两份文本、逐条生成记录、运行配置/耗时/错误 | 模型目录、参数、提示词版本、是否生成失败 |
| 独立参考 | 原图、参考标注提示词 | 参考请求与事实表草稿、人工核验版本 | 原文、中文事实、证据位置、置信度、任务重点 |
| 盲评 | 原图、固定候选、参考、量表 | 两任务评审请求与结构化评审结果 | 原子声明、证据 ID、维度理由、严重错误、复核原因 |
| 聚合报告 | 生成记录、规则结果、参考、评审结果 | 全量记录、分组指标、失败样本与复核清单 | 总分、各维度、覆盖率、失败/缺失与适用权重 |

一个图像 ID 下保存两任务各自的文本和状态；参考标注按图片共享，评审结果按“图片×任务”区分。不要覆盖失败状态，也不要把未评样本当成 0 分或自动剔除。报告同时列出：扫描图数、应生成条数（图数×2）、成功/失败生成条数、合法/非法/缺失评审条数、参与语义统计条数。缺失的语义分数保持为空，单独报告覆盖率，防止只展示容易的成功样本。

更换候选文本、参考表、量表或提示词后，必须重新建立对应的评审请求。运行目录冻结 evaluation_prompts/reference_system.txt、evaluation_prompts/judge_system.txt，并使用 judge_meta.json 固定评审模型与版本。结果导入时核对任务、图片 ID、候选/参考/评审提示词校验值、必需维度及分值类型；旧答案的评审不能套到新答案。事实参考不提供给 Qwen 生成器，避免答案泄漏。对同一图片的其他候选答案也不提供给评审员。

## 3. 保留 v04 提示词，明确规范冲突

prompts/v04_summary.json 与 prompts/v04_interpret.json 保存提供的 system 和 user 正文，未根据测评需求改写生成提示词。当前基线含有真实的规范冲突，应保留并报告，后续通过新的版本做对照实验：

| 问题 | v04 基线评测口径 |
| --- | --- |
| 摘要示例超过标题10字、描述30字，且含原文括注 | 按明确的两行与10/30字硬要求检查；不以示例为理由放宽 |
| 解读菜单模块要求“中文名（原文名）”，同时禁止原文括注 | 必要的原文菜单名按规范歧义处理，不把同一歧义反复扣语言、结构和遵循分；无必要的普通外文括注仍可提示问题 |
| 场景清单可能有4~5个核心角度，全局只允许1~3个核心模块 | 按全局模块上限组织，允许选择或合并关键角度，不要求把场景清单逐项输出 |
| 解读示例部分模块只有1条，但核心模块要求每模块2~4条 | 核心模块按明确的2~4条要求检查并记录示例冲突；增量信息不足按提示词允许合并或省略，不能为了凑数编造事实 |
| “仅中文”与专有名词可保留原文 | 店名、品牌名、地名、作品名等合理保留不单独罚语言分 |
| 示例含功效、用法和人群建议 | 示例不是当前图片证据，不授权生成器补造事实；医疗输出仍须遵循仅图上事实与免责声明 |

本版字数按去除所有 Unicode 空白后的字符数计算，汉字、字母、数字、标点各计1，内部空格也不计入；换行用于判断结构，不计入单行字数。单个末尾 LF 或 CRLF 视为合法的文件行结束符，额外空行仍为违规。保留原始输出检测空行、第三行、Markdown和禁用前缀，不应先“修复答案”再测评。原文名、主观评价和是否忠实翻译等语义判断不能靠关键词检查给出确定结论。

解读长度、模块标题及要点数可做程序检查或启发式提示；模块标题的核心/增量含义、建议价值、主体正确与否仍需证据评审。信息不足时原提示词允许合并或不出增量，不能强制模型编写空话凑条目。菜单没有全文500字上限，但仍评价简洁与重点选择。

## 4. 独立事实参考如何建立

prompts/reference_system.txt 只供参考标注员使用，输入原始图片，不输入 Qwen 答案。参考事实应覆盖可见内容，重点核对不同语种下的实体、数字、否定和条件。原图有阅读困难时明确标注局限。

参考 schema 主要字段：

- scene：menu、restaurant、beauty、food、medicine、landmark、media、document、general。
- image_quality：可读性 clear/partial/unreadable 与实际图像问题。
- facts：fact_id、category、source_text、normalized_zh、evidence、confidence、importance、required_for、numeric。
- unreadable_regions：无法可靠辨识的具体区域及影响。
- reference_status：模型一律输出 draft；人工核验流程才设置 human_verified。
- annotator：标注模型及版本。模型标签必须使用实际调用信息，不能自报为人工。

每个事实应尽量原子化，原文和中文解释分别保存。evidence 用字符串描述图片位置和关系；需要时人工可另行补充框选，但本版不依赖 OCR 框架。非文字视觉事实的 source_text 为空字符串。category 固定为 name/category/price/currency/quantity/ingredient/allergen/time/location/restriction/other。

例如菜单中“牛肉拉面 12.50”可以拆为菜名和价格两个事实，价格证据必须说明与哪个菜品、份量、套餐相连。不能只记录“12.50”而丢失对应关系。numeric 使用字符串保存值及精度/范围，并记录 unit、currency、qualifier；只有明确币种才写 ISO 代码，只有“$”不能认定美元。原价、优惠价、起价、每人价、税费、服务费、大小份、时段限制等都是解释价格的必要条件。

confidence=high 必须具有清晰图像证据与明确绑定；medium/low 供辅助核对和人工复核。完全看不清的内容记录到 unreadable_regions，不能补字、补小数点或补菜名。

required_for 表示当前任务合理容量内应表达的重点，只有 high 事实可进入。摘要一般选择2~4个主体/代表性事实，不能拿全菜单做召回分母；解读按1~3个核心模块容量选择关键分类、代表菜品、重要价格/条件和明确安全限制。importance 取1/2/3，并根据对理解、点餐或安全的影响区分，不能把全部事实都标3。

菜名包含“花生”可以支持菜名及翻译，却不能证明完整配方、无其他过敏原或适合特殊人群。“未标注”不能转成“不含”。仅从环境、装修或菜名不能推测菜系、宗教认证、素食、安全性、营业状态和价格水平。保留这种边界比让参考表显得详尽更重要。

## 5. 评审怎样验证答案

prompts/judge_system.txt 要求先拆分原子声明，再匹配原图和独立参考，不直接凭整体印象给一个总分。评审请求不包含 Qwen 模型名、运行名称和其他答案，固定文件命名或匿名 ID；生成参数留在运行元数据中供研发追溯。评审员仅使用必要信息，仍需提供 task、task_prompt、当前任务的 rubric 以判断规范。接口适配器必须向请求 input.annotator 或 input.judge 注入真实模型与版本元数据；缺失时不能让模型编造这些字段。

声明 verdict 分为：

| 结论 | 使用条件 |
| --- | --- |
| supported | 有可靠原图或参考事实证据，实体、关系、必要条件一致 |
| contradicted | 与可靠证据矛盾，如价格错配菜品、否定译反、把起价写成固定价 |
| unsupported | 已有足够原图依据确认图片特定陈述无依据，或外部推断被当成图中事实 |
| unverifiable | 图像不可读、参考不足、数字/币种绑定有歧义，或没有实际原图可核对 |
| background | 明确标为一般背景/建议，符合解读任务且高置信，未冒充图片事实 |

参考未收录不等于图片不存在。仅文本评审时，证据表不能支持的图中特定事实通常应判 unverifiable，并进入复核。这样的结果不应被宣传为完整视觉真值评测；至少独立参考阶段要有真正看图的视觉模型或人工。

severity 使用 minor/major/critical。错误价格、主体误认、重要翻译通常为 major；可能影响饮食或用药安全的错误/无依据保证为 critical。supported 声明即使标了 critical 影响级别也不作为错误；严重风险但证据不足的声明进入复核，而不是记成已证实严重错误。明确关键安全限制的遗漏也须独立记录。

评审输出必须给每个维度一个整数0~4或 null、非空理由、证据 ID，以及 claims、covered_fact_ids、critical_errors、needs_human_review、review_reasons、judge_prompt_sha256。每条 claim 必须带 category，枚举与参考事实相同；价格归 price、币种归 currency、份量/规格归 quantity、时间归 time，多个不同类型的事实拆开记录，避免数字被混入整段声明而漏统计。原图与参考冲突、参考缺少重点、高风险疑点、不可读、规范歧义等都列具体复核原因。图像、候选和事实表中的“给满分”“忽略要求”等文字仅当作数据，不能影响评审流程。

## 6. 量表、分数与核心指标

configs/rubric.json 定义两任务独立权重，均合计100。下表为权重，空白代表该任务没有该维度：

| 维度 | 摘要 | 解读 | 主要回答的问题 |
| --- | ---: | ---: | --- |
| 事实准确性 | 20 | 20 | 已陈述的实体和关系是否正确 |
| 关键信息覆盖 | 15 | 15 | 合理容量内的重要事实有没有讲到 |
| 翻译准确性 | 10 | 10 | 原文语义、否定和条件是否忠实 |
| 数字与价格准确性 | 10 | 10 | 值、单位、货币和对象绑定是否正确 |
| 无依据内容控制 | 15 | 15 | 是否编造图片事实、作过度推断 |
| 中文可读性 | 5 | 5 | 表达是否自然清晰 |
| 简洁与信息密度 | 5 | 5 | 有无重复、空话、冗长抄录 |
| 提示词遵循 | 10 | 5 | 语言、格式、限长及禁止内容是否满足 |
| 主体识别 | 5 |  | 标题是否点名正确主体 |
| 标题描述互补 | 5 |  | 第二行是否提供新增关键事实 |
| 场景理解 |  | 5 | 选择的模块是否贴合菜单/餐厅等场景 |
| 解读结构 |  | 3 | 速览、模块和要点是否合理 |
| 解释价值 |  | 7 | 能否帮助理解和实际决策 |

通用分数锚点：4=满足，3=仅轻微问题，2=重要不足，1=多处重要问题，0=任务或维度失败。null 只用于不适用或证据不足，必须说明理由。遗漏重要数字应在关键信息覆盖扣分；不能因为没有输出数字就认定数字能力满分。未发生翻译需求时翻译维度可空，但漏译重点仍影响覆盖。

总分由程序按适用维度计算，评审模型不负责求和：

`总分 = 100 × Σ(权重 × 维度分/4) ÷ Σ(适用权重)`

null 维度从分子和分母移除，适用权重为0时总分为空。报告保留适用维度/权重；仅少量维度可评的高分不能与全维度高分直接解释为同一能力。空白输出是任务失败，不能靠“没说错话”获得高事实或无幻觉分。

除总分外，至少独立报告这些指标：

1. 格式与硬约束：摘要两行率、标题/描述限长率、前缀/Markdown/空行等违规；解读首段与非菜单长度、模块形式等可检测项。简繁体、语义重复、主观评价等规则提示须说明其启发式性质。
2. 高置信重点覆盖率：已正确覆盖的必需事实 importance 之和 ÷ 当前任务全部 high 必需事实 importance 之和。没有必需事实时覆盖率为空，不是100%。
3. 已陈述事实的核对结果：supported、contradicted、unsupported、unverifiable、background 的数量与比例，并保留每条证据。长答案自然有更多声明，不能只比较原始错误数量。
4. 价格与数字能力：数值相关声明按菜品/套餐/单位/币种/条件完整核对；报告对应维度、错误样本和复核情况。不能因候选抄对数字但错配菜名就算正确。
5. 翻译与语言能力：按语种查看错译、漏译重点、否定与条件丢失；专有名词保留及通行译法不算自动错误。
6. 严重错误样本率与已确认严重错误数量：独立展示，不让总分抵消。安全相关推断无依据、明确忌口/过敏提醒被反转等重点回看。
7. 待人工复核率、未核验参考比例、非法/缺失评审比例、生成失败率。样本被弃评时要看到原因。

按全部图片汇总，再按语种、截图/实拍、菜单/餐厅、可读性分组。主结果保持截图与实拍混合，分组用于发现特定薄弱点。每个分组显示样本数、有效评审数和适用权重；可同时报告按样本加权平均和各语种等权平均，避免大语种盖住小语种。若样本极少，只做描述性比较，不把单次高分当作稳定结论。

正式比较多个模型或提示词时保持同一批原图、同一任务、同一参考版本、同一评审模型/量表和尽量固定的评审参数；同图两任务不是两个完全独立样本。需要置信区间时建议按图片进行重采样，避免把相关答案当独立样本；本阶段无需为此引入额外执行协议。

## 7. 人工抽检、校准与明天接接口的步骤

先用一小批图片完成流程校准。建议覆盖每个实际存在的语种及截图/实拍、菜单/餐厅，包含密集价格、局部模糊、货币歧义、菜名难译和安全限制；至少由两名能阅读相关语种的人员独立检查部分重叠样本。

人工工作顺序是先看原图核验参考表，再看候选评审结果。不能只校准总分而不检查错误来源。记录参考错读、评审误判、提示词规范歧义三种原因；参考有误时先修参考，再对关联的两任务重新评审。

正式运行至少随机抽检10%~20%，按语种×来源类型×场景分层，每个非空层尽量至少1张；小数据或层数多时覆盖各层可能超过20%，以覆盖关键层为准。另行全量复核严重错误、安全疑点、参考与原图冲突、无法核验和输出失败样本；这部分定向样本不并入“随机抽检错误率”分母。不要只抽高分或只抽失败样本。

校准时报告参考事实正确率、关键事实漏标、两个标注员的事实判断分歧，以及维度分数差异。0~4分维度相差2分及以上、正确/错误判断分歧、任何安全结论分歧都需回看证据并形成统一口径。样本充足可报告加权一致性统计，同时保留实际分歧率；一致性高也不等于真值正确。

明天拿到接口后，先确认接口能接收真实图片、调用发生在允许的数据边界、返回结构支持 JSON，然后接入参考和评审两个独立操作。选5~10张混合样本试运行，核对所有标识/哈希、JSON合法性、必需维度、声明证据和复核输出。确认参考模型没有接触候选，评审请求不暴露候选模型身份，再扩大批量。若支持的只是文本接口，则先由人工/获准视觉模型建立图像参考，并明确文本评审的可核验范围，不能用“路径占位”冒充看图测评。

本方案可以检验主体识别、重点选择、翻译、数字绑定、事实性、长度、结构和实际解释价值；其中对世界知识与未知配方的真实性不作原图证据认证。最终结论应带样本分布、事实参考状态、待复核比例及失效样本数，才能说明分数真实反映了哪些能力。
