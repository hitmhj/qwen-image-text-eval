# 三任务、两独立测试集的细粒度测评设计

每张图片生成摘要、解读、点餐推荐三份答案，三任务分开评测。推荐额外输入一条固定需求，不能看图后挑一个容易的要求。生成使用本地 Qwen3.5-35B-A3B，模型目录在 .sh 中预留；第一平台自动生成含完整原图字节和三任务结果的 handoff.json。第二平台只复制 evaluate.py 与 handoff.json，运行 python evaluate.py handoff.json，标准库即可完成读取与报告。接口尚未接入，当前准备参考请求和预览，语义评分保持未测。

本版为 schema_version=2、evidence_rubric_v2。摘要、解读生成提示词原文保持 v04，新增 v01_recommendation。完整 system/user 全文在三个任务提示词原文.md，与 prompts/ 中 JSON 逐字一致。v2 合并重叠评分维度并新增推荐，不能把其总分直接与 v1 比较。

## 1. 两套数据与数据边界

primary 是原图片测试集，按“图片总目录/语种/截图或实拍/图片”读取；截图、实拍统一生成和评测，同时保留元数据用于分组。menu_reference 是独立的菜单参照测试集。两者各自运行三任务，通过同一个 handoff.json 交接，dataset_id 始终保留。第二平台 results.json 按数据集保存参考、评分和指标，HTML 分开呈现两套结果；不能把两来源的图片、分母、均分或排名合并。同一文件哈希出现在两套数据中也不能改变测试集归属。

菜单与餐厅整体照片分开报告；餐厅照片在原解读提示词中对应通用模块，推荐缺少菜单时可以合理说明不足。不要用语种目录、文件名、截图类型猜图片内容。原图可读性与来源难度应在分组中显示，而不是筛掉困难样本。

仓库保存代码、配置以及这次整理的公开来源菜单集，不保存您的原始图片、模型、生成文本或测评结果。跨平台复制 handoff.json 使用您的既有内部流程。生成阶段仅加载本地模型，第二平台的真实 GPT 接口由您提供后接入。

dataset_id、image_id、图片SHA-256、候选文本SHA-256、规范化参考JSON SHA-256、judge_prompt_sha256、task_prompt_sha256及requirement_sha256共同绑定数据与版本。后两者分别绑定完整任务提示词对象、完整推荐需求对象，不能只绑定需求id；推荐之外的评分requirement_sha256为null，参考在无推荐需求时为null。评审必须实际接收原图像素，附件路径本身不等于已看图。真实annotator/judge模型和版本由接口适配器注入，不让模型自报虚构值。

source_evidence_mode按适配器真实输入区分image_and_reference和reference_only，复制请求expected_source_evidence_mode。前者必须真正附图像像素，后者只用参考表，不能自报看过图片；请求模式错误时先修请求再评。两个证据模式的结果应注明模式及未知率，不能把仅参考的低幻觉率理解为已经完整看图核验。

## 2. 三任务与固定需求池

摘要回答“图是什么、最重要的可见事实是什么”；解读回答“如何理解可见内容”；推荐回答“在这张菜单、用户预算和限制下能否给出可信组合”。三种任务不能以同一套长答案召回指标替代。

configs/requirements_pool.json 的版本是 requirements_pool_v1，固定16条，id为req01..req16。所有预算是CNY总预算。一次运行按固定seed与图片标识确定抽取结果并留存需求id、原文、结构化constraints、池版本/指纹和实际展开user文本。更换池、seed或抽取结果应新建运行，不能在失败后重新抽取。测试集分开保留分布，不宣称16条难度天然均匀。

| ID | 需求原文 |
| --- | --- |
| req01 | 我一个人，总预算50元人民币，不能吃辣，请推荐一份主食。 |
| req02 | 我一个人，总预算80元人民币，喜欢鸡肉，优先推荐鸡肉类主食。 |
| req03 | 我一个人，总预算60元人民币，不吃牛肉，请推荐一份主食。 |

| req08 | 我一个人，总预算80元人民币，不能吃辣，需要一份主食和一杯无酒精饮品。 |

| req16 | 我一个人，总预算60元人民币，想吃一份主食，偏好不带汤的。 |

每条constraints保留相同字段：

- budget：amount为十进制字符串，currency=CNY，scope=total；总预算不能乘人数。只有明确人均时才能另行设定相应范围，本池没有人均预算。
- diners：人数；多人各一份时也核对个人分配，不只看总数。
- hard_constraints：id/type/value/scope，类型为spice、ingredient、allergen、diet；scope允许all或person_1等。明确不能辣、不吃牛肉/海鲜、过敏、严格纯素是硬约束。
- preferences：同样保留id/type/value/scope；鸡肉、低价、蔬菜偏好、喜欢辣、特色、多样性、不带汤等不应覆盖硬约束。
- meal_requirements：min_main_dishes、min_dishes、exact_main_dishes、min_non_alcoholic_drinks四键均存在，未指定为null，指定为整数。req07是至少3份主食；req06/08含至少1杯无酒精饮品；每人一份落实总份数及人数分配。

req10明确不是严格素食；req15的“希望至少两种”按软多样性偏好处理，min_dishes=null；req13只有person_1不能辣，person_2喜欢辣是偏好，不扩大为所有人不能辣。菜单未给食材/辣度信息时这些硬约束可能不可确认，这种难度正是需要测量的能力，不降低要求换取成功率。

推荐user使用固定模板：
`请根据图片和下面的点餐要求给出推荐。\n点餐要求：{requirement}\n补充信息：{context}`
补充信息只能来自实际输入，缺失不能自动补汇率、辣度、配方或过敏原。

## 3. 单文件交接与平铺输出

生成与测评独立部署。第一平台自动在输出根目录保存唯一交接产物 handoff.json，其中按数据集包含三任务结果、状态、固定需求、提示词、图片身份和完整原图字节。原图使用 base64 表达，读取时按 SHA256 核验；未压缩、缩放或裁剪。内部生成记录继续保持 schema_version=2。断点目录留在第一平台，第二平台不读取任何第一平台路径。

第二平台只复制 evaluate.py 和 handoff.json，然后运行 python evaluate.py handoff.json。默认在交接文件所在目录平铺保存：

| 文件 | 作用 |
| --- | --- |
| results.json | 两套数据分别保存参考、评分、指标、证据、运行状态及版本指纹 |
| report.html | 分开展示两套数据的详细结果、原图、失败与复核信息 |
| reference_requests.json | 接口未接入时准备的原图事实/推荐可行性请求，不包含Qwen答案 |

两个测试集可以共用一个交接文件和输出目录，程序在文件内按 dataset_id 严格隔离，统计分母不合并。旧候选哈希、错误参考哈希、跨数据集回包或不一致提示词回包应拒绝。更换模型、需求、提示词、量表或事实表后重新建立对应请求；重新标注参考后重评关联候选。参考不注入生成器，评审请求不包含待测模型身份、其他候选或测试集的历史分数。

已有回包可通过 --references、--scores 导入，支持 JSON 数组或 JSONL。原有 reference/score/report 子命令仅作为兼容入口，新流程不要求手动管理阶段文件、图片目录、image-root 或第一平台的目录结构。

参考构造和评分在逻辑上独立。默认一次运行按参考、评分、报告顺序执行；需要分别运行时用 --stage reference 或 --stage score，同一个 results.json 保存并自动读取参考，不增加交接文件或目录。

应生成条数是有效图片数×3；另外保留无效图片、缺失、生成失败、截断、无参考、非法/过期/缺失评审和参与统计条数。缺失语义分保持为空，不能当0分，也不能删掉失败样本仅展示容易案例。

## 4. 独立参考不是另一份“标准答案”

先让视觉标注员只看原图与固定需求，建立事实表；然后才让评审员核验候选。一个大模型写的答案可能同样误读价格、补配方或猜辣度，因此模型结果一律draft，不能自称human_verified。人工核验后才升级状态，报告同时给核验比例。

reference schema保留dataset_id/image_id/image_sha256、scene、image_quality、facts、unreadable_regions、reference_status、annotator，并新增requirement_sha256、recommendation_feasibility。需求换预算、人数、忌口或补充内容，即使id没变，指纹也改变，旧可行性不能复用。事实包含：

`{fact_id,category,source_text,normalized_zh,evidence,confidence,importance,required_for,numeric}`

category固定name/category/price/currency/quantity/ingredient/allergen/time/location/restriction/other。source_text保留可辨原文，非文字事实为空字符串；normalized_zh忠实翻译；evidence指出位置与关联对象。confidence为high/medium/low，importance为1/2/3。只有high事实进入required_for，低置信不列必需召回项。required_for允许三任务名称。

价格必须绑定菜名、份量/规格、套餐、大小份、原价/优惠价、时段及必要条件，不能只留脱离对象的数字。numeric存十进制或范围字符串、unit、currency、qualifier；仅见“$”不推定USD。看不清的小数点、币种、菜名记录不可读，不能补齐。

摘要required_for一般是容量内2~4个主体/代表性重点，不能要求召回全菜单。解读按1~3核心模块选重要分类、代表餐品、价格与限制。推荐多解，不以某一组菜名作为唯一真值；仅把所有可行方案共用的关键高置信计费/安全/套餐规则设为必需，其他候选所选菜品仍可由完整事实表核验。

菜名中的鸡肉不证明完整配方，更不能证明无牛肉/海鲜、无花生、严格纯素或不辣。未标注不同于不含；过敏要求可能需要交叉接触信息。餐厅环境不能支持菜系、价格、服务质量或具体地址的猜测。

recommendation_feasibility在有需求时为：
`{requirement_id,status,reason,evidence_fact_ids,fees_status,mandatory_fees}`
无推荐需求可null。status为：

| 状态 | 意义 |
| --- | --- |
| feasible | 至少存在一组可证实满足全部硬约束的图中组合，reason列存在性见证、数量/费用和证据 |
| infeasible | 可靠证据确认图中选项无法满足硬约束，结论限于可见选项 |
| unknown | 辣度/配方/过敏原、价格/费用、对象/份量或输入汇率等不足，不能证明有解或无解 |
| not_applicable | 图中没有可用菜单/餐品信息，任务不适用 |

参考可行性必须先于候选独立判断，不为了候选方案改成feasible。局部菜单不能推断整家餐厅没有合适菜。外币菜单配人民币预算没有实际输入汇率时为unknown，不允许查询常识汇率代替固定输入。

fees_status固定complete/partial/unmarked。complete须有明确含税、无额外费用或实际计费规则已充分覆盖；partial是看到了收费但金额/币种/基数/范围不足；unmarked是图中未标费用口径，不能猜成0费或complete。只记录图示真实收费，不凭空添加图外税费。费用不完整时是否低于预算通常unknown；若已知必要费用下界已经超过上限，仍可证实超支，只有图中所有组合的下界均超支才据此判infeasible。

GT mandatory_fees每项为fact_id、name、kind、amount、currency、scope；fact_id引用高置信真实费用事实，kind为flat/percentage/minimum_spend，amount为十进制字符串或null（percentage的“10”表示10%），currency明确时为ISO代码，scope为per_order/per_person。图示范围或基数无法确认时partial/unknown，不能默填默认；schema允许时可用可选basis记录原图明确的基数说明。最低消费是支付门槛，复算只补足差额，不整额重复加入。费用事实与完整口径的证据位置保存在fact.evidence、reason和evidence_fact_ids。

## 5. 候选核验与推荐机器复算

评审先把标题、主体、菜名翻译、价格、数字、限制和建议拆成原子claims，每条category必填，以免数值混在整段other中漏统计。verdict为supported、contradicted、unsupported、unverifiable、background：有证据支持、与证据矛盾、足以确认无依据、不可核验、明确的一般背景。参考缺失本身不证明候选错误，只有路径没有原图时需注明视觉盲区。

supported至少引用一个high/medium参考事实，contradicted至少引用一个high冲突事实；只有low或不足以确证的内容用unverifiable。reference_only模式严禁unsupported，未在参考出现的声明用unverifiable而不是判编造；image_and_reference也须有充分实际原图依据才判unsupported。图中可见但未入参考时，先暂列unverifiable并要求修参考再评，不能新增虚构ID。covered_fact_ids只包含当前任务high必需事实且有supported声明。主体、数字或条件错写不能记覆盖。

severity为minor/major/critical；价格错配、主要翻译错误等为major，错误安全保证或用药信息可能critical。supported的影响级别不算错误。critical_errors只计已证实严重错误及明确关键安全限制遗漏；未知安全疑点进入人工复核。

评分回包必有task_prompt_sha256、requirement_sha256、source_evidence_mode，按请求实际元数据复制。推荐评审额外输出recommendation，摘要/解读该字段为null。推荐对象包含requirement_id、disposition、requirement_checks、plan。disposition为confirmed/conditional/unable，表示候选提出确认方案、条件方案或无法确认。候选写“符合”不能自动判符合。

requirement_checks逐项核对程序提供的required_constraint_ids，严格对应budget、diners、hard_constraints各id、meal_requirements各非null键，不能漏项或重复。每项status=met/violated/unknown并给reason/evidence_fact_ids。软preferences不加入硬约束成功分母，仍在推荐价值评价。未证实不辣、无过敏原或纯素时必须unknown，不以常识或自信文风判met。

plan从候选抽取，不替其补正确方案。金额/数量使用十进制字符串或null，由Decimal复算：

- items：name、quantity、unit_price、currency、price_fact_ids、person。单价绑定正确规格，人数分配明确时写person_1等，未表达分配为null。
- subtotal：候选小计，与Σ数量×单价比较。
- mandatory_fees：name、amount、currency、reason、evidence_fact_ids；与独立GT收费规则逐项核对图中必付税费、服务费等，费率应说明基数。候选漏列费用不能导致GT也漏算；复算最低消费只补差额。
- total、currency：候选包含其列明费用的总价，漏必付费用不能靠复算正确掩盖。
- fx：显式输入的from_currency、to_currency、rate、source；1单位from=rate单位to。没给汇率就null，跨币种不能直接相加。
- budget_total、budget_currency：候选实际费用换算到预算币种的合计，不是预算上限；同币种budget_total=total，无换汇依据则null。预算上限来自constraints.budget.amount，当前全部是总预算。

声明、菜单事实及算术分别核验：算对总和不代表抄对单价，也不证明忌口成立。未知费用不替候选猜值，GT费用partial/unmarked时不能宣布最终预算met，但已知下界超支可判violated。安全地拒绝或明确待确认可以是高质量输出，不会因未强填全部模块而判格式失败；但不把这种诚实未知统计成已确认推荐成功。

## 6. v2量表、诊断与分母

维度评分0~4/null：4无实质问题、3轻微问题、2重要不足、1多处重要问题、0失败。null仅不适用或证据不足，已观察错误不能转null。维度reason须非空，证据ID存在。评审不计算加权总分。

| 维度 | 摘要 | 解读 | 推荐 |
| --- | ---: | ---: | ---: |
| factual_accuracy 事实性 | 35 | 35 | 25 |
| key_information 重点覆盖 | 25 | 25 |  |
| translation 翻译 | 10 | 10 |  |
| numeric_accuracy 数字绑定 | 10 | 10 |  |
| readability 可读与简洁 | 10 |  | 10 |
| prompt_following 提示词遵循 | 10 | 5 |  |
| structure 场景与结构 |  | 10 |  |
| usefulness 解释/推荐价值 |  | 5 | 15 |
| requirement_following 需求处理 |  |  | 30 |
| budget_accuracy 费用核验 |  |  | 20 |
| 合计 | 100 | 100 | 100 |

v2不再单独给无幻觉、简洁、主体、互补和场景重复加权：事实性包含无依据内容控制，重点覆盖兼顾摘要主体/互补，可读性兼顾简洁，解读结构兼顾场景。这些能力仍能从声明、规则和理由诊断，而不会在总分反复计权。

总分=`100×Σ(权重×维度分/4)÷Σ适用权重`。null移出分子/分母，适用权重0时总分空。低适用权重高分不等同于完整维度高分。候选空白是任务失败，不能以没有编造拿高事实性分。

所有指标在primary/menu_reference内分别、再按三任务分别报告：

1. 生成/评审覆盖：图数、预期三任务数、成功、失败、缺失、非法/过期及已评数。未测不计零分。
2. 规则通行：摘要两行/10与30字、解读速览50字/非菜单500字/模块、推荐350字及状态/所需结构。保留原始文本，不能先修复再计分。语义重复、评价、简繁体等启发式提示不当成确定语义结论。
3. 事实诊断：令S=supported、C=contradicted、U=unsupported、X=unverifiable（background独立）。事实准确率S/(S+C+U)，幻觉率U/(S+C+U)，矛盾率C/(S+C+U)，未知率X/(S+C+U+X)。分母0为空；不把矛盾塞进幻觉率，也不把未知当正确。
4. 高置信重点覆盖：正确覆盖importance之和/当前任务high必需事实importance之和；分母0为空，推荐不能以固定方案菜名做唯一召回目标。
5. 数值诊断：数值类别price/currency/quantity/time中，已判可核对声明的准确率及未知比例单列。全部unknown不算满分，同时检查实体/币种/规格/套餐绑定。
6. 推荐可行性与成功：独立参考的feasible/infeasible/unknown/not_applicable比例；在GT=feasible子集中，仅全部硬约束checks=met才记成功，预算unknown不能通过。另列条件方案、无法确认、合理拒绝与复核比例，不能用诚实未知提高成功率。需求处理高分和成功率是不同指标。
7. 严重错误率/数量、无依据安全保证、复核率、参考人工核验比例，均独立展示，不被总分掩盖。

保持截图与实拍混合主结果，但分组查看语种、来源类型、菜单/餐厅、可读性、需求id、GT可行性等；每组显示样本数及有效分母。大语种样本多时可同时提供按样本加权和按语种等权平均。小样本只做描述，不能把单次高分当稳定结论。比较模型/提示词时保持同图、同需求、同参考/量表/评审版本；如统计置信区间，按图片而非同图三答案独立重采样。

## 7. 保留原提示词与规范冲突

v04 summary/interpret JSON原文未修改，推荐为新v01。冲突不靠悄悄改生成prompt解决，评审口径明确：

| 原文冲突 | 评审处理 |
| --- | --- |
| 摘要示例超10/30字、含原文括注 | 以明确两行和硬限为准，说明示例冲突 |
| 菜单要求“中文名（原文名）”，又禁原文括注 | 必要菜单原文记录歧义，避免多维重复扣分；普通无必要括注仍提示 |
| 场景列4~5核心角度，全局1~3核心模块 | 可选择/合并关键角度，以全局上限为准 |
| 示例每核心只有1条，要求2~4条 | 以明确核心条数为准，增量可按允许合并/省略，不能编事实凑数 |
| 仅中文与专有名词可保留原文 | 合理品牌/店名/地名/作品名不单独罚分 |
| 示例含功效、人群、用法 | 不作为当前图证据；医疗仍仅图上事实并加免责声明 |

字数去除所有Unicode空白，汉字、字母、数字、标点各1；摘要末尾单个LF/CRLF作为合法文件行结束，额外空行违规。菜单无全文500字上限，但仍评价信息选择与可读性。推荐不可确认时允许简要理由和补充信息，不强填四模块。

## 8. 人工校准与接口接入

先选5~10张混合样本试通请求/回包，确认接口真正读图、数据边界获准、JSON结构和哈希正确。参考标注与候选评分分开调用，不能把Qwen答案塞入参考请求。schema2新增dataset_id、三任务、推荐可行性/计划，旧schema1回包不能套用。

正式运行随机分层抽检10%~20%，覆盖语种×截图/实拍×场景和推荐可行性/需求类型；每个非空层尽量1张，小数据可超过20%。另全量复核严重错误、安全未知、参考冲突、无汇率、不可核验和生成失败样本。定向复核不并入随机抽检错误率分母。

至少两名能阅读相关语种的人独立核查重叠样本，先看原图修参考，再看候选评分。记录参考错读、评分误判、规范歧义与可行性分歧。0~4分相差2及以上、正误判断不同、可行性或任一安全结论分歧都回到证据解决。修参考后重评相关三任务，不只改总分。

若接口只支持文本，先由人工或获准视觉模型建立参考，并明确文本评审对未收录事实的盲区；不能用路径冒充看图。接口真正接入前，HTML可显示已生成、规则和未测状态，不能展示虚构GPT质量分。最终结论带测试集分布、有效分母、参考核验状态与待复核比例，才能解释分数反映的能力。
